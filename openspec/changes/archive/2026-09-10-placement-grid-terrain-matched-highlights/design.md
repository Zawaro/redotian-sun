## Context

`PlacementGridOverlay` (scripts/core/PlacementGridOverlay.gd) renders build-mode
highlights as one `MultiMesh` of flat chamfered octagons, all at
`max(corner heights) + PLANE_Y_OFFSET` with identity orientation. This was
decision D1 of the archived `placement-grid-highlights` change (#352), which
flagged "flat cells may look wrong on steep terrain" as an accepted risk. It
now looks wrong: on any non-flat cell the octagon floats over the ramp.

The terrain's authority is the vertex heightfield: `TerrainSystem` stores
per-vertex integer heights, and each cell's four corner heights
(`get_cell_corner_heights`, world order NW/NE/SW/SE) fully determine that
cell's surface. The catalog layer (`TerrainObject` objects, generated by
`tools/isotem`) stores the same corner pattern per object plus a `crease`
triangulation label; the GLB submeshes are baked visual tessellations of those
patterns (corner heights baked to n × `HEIGHT_STEP`). Placement of the drawn
tile uses only data: min-corner height, direction rotation, corner-pivot AABB.

Spike result (pre-implementation): the `crease` label is a pure function of
the corner pattern. `tools/isotem/generate_tres.py::derive_crease` computes it
from corners alone — all-equal or adjacent-pair-high → `"flat"` (planar),
one-unique-high or one-unique-low → `"x"`, opposite-pair-high (saddle) →
`"y"` — and re-derives it after rotating corners for each directional variant.
Therefore the engine-side geometry needs no catalog lookup at all: the patch
is a function of four corner heights, using the same split rule
`derive_crease` encodes. Spike 1.1 confirmed this 24/24 against every
object variant (see Open Questions).

## Goals / Non-Goals

**Goals:**
- Non-flat rendered cells (corner heights not all equal) display a mesh that
  matches the terrain: the four corner positions, one of two triangulation
  diagonals per the `derive_crease` rule, lifted `PLANE_Y_OFFSET`.
- The matching treatment covers white-region cells, green and red cells under
  the ghost, at no dependency on terrain art, catalog resolution, or the GLB.
- No vertical or near-vertical faces are ever produced (the cliff constraint
  holds by construction).
- Flat cells keep the current octagon; all color-assignment logic is untouched.
- Verification that a generated patch reproduces the baked catalog/ GLB
  tessellation for every slope object variant (the "matching" acceptance
  gate).

**Non-Goals:**
- Map editor highlight paths (`EditorGrid`, `AssetPreviewController`) —
  separate code, unchanged.
- `can_place`, `footprint_buildable`, `flatten_footprint`, or any placement
  validation behavior.
- Multi-cell cluster objects (cliffNN/rampNN clusters) — they do not reach
  runtime `_cells` today (map import recomputes cells from the vertex grid);
  if that ever changes, the corner-based rule already handles them.
- Changing the octagon's 95%/chamfer styling, colors, or alpha values.

## Decisions

### D1: Geometry is a pure function of the cell's four corner heights
The patch builder takes four corner heights (× `HEIGHT_STEP`) and four corner
world XZ positions and emits up to two triangles. No `TerrainCatalog`
resolution, no GLB clone, no `object_id` lookup.
*Why:* the corner data is the same authority validation and collision already
read, so the highlight cannot desync from the terrain; the overlay renders
identically under any theater or missing art; and the spike proved the
triangulation rule is re-derivable from corners (no per-variant table).
*Alternatives:* cloning the catalog GLB submesh (pixel-exact art match, but
couples the overlay to art lifecycle and reduces "no wall" to a normal-angle
heuristic), or a catalog-lookup variant (still needs the crease mapping the
rule makes unnecessary).

### D2: Split-diagonal rule (engine-side form of `derive_crease`)
Corner indices in world order: 0=NW, 1=NE, 2=SW, 3=SE. The cell's diagonals
are {0,3} (NW–SE) and {1,2} (NE–SW).
- Corners coplanar (test: the four 3-D corner points have zero tetrahedral
  volume, i.e. `(p1-p0) × (p2-p0) · (p3-p0) == 0`) → plain quad, the
  {0,3} diagonal by convention (the internal edge is invisible for the
  unshaded material).
- Exactly one unique corner (max or min) → the diagonal that does NOT pass
  through the unique corner. Yields one flat triangle of the three
  non-unique corners plus one sloped triangle — the same split the baked
  mesh uses.
- Two diagonally-opposite corners share the max (saddle) → the diagonal
  joining that pair; both triangles carry the raised edge.
- Two adjacent corners share a non-planar max (pattern like
  [max, max, mid, min] — not in the current catalog, possible on hand-built
  vertex grids) → fixed {0,3} diagonal. `ponytail:` if such patterns appear
  in maps, score both diagonals against the bilinear surface and take the
  smaller-deviation one.
*Why:* on all corner patterns that exist in the catalog this is exactly
`derive_crease`, the rule the catalog generator bakes into every object
variant, re-expressed in world corner indices (verified 24/24 in the 1.1
spike). Note `derive_crease`'s own "adjacent-pair-high → flat" branch is a
heuristic (a [max, max, mid, min] pattern is labeled flat there but is not
coplanar); the engine rule uses the exact coplanarity test instead, which
agrees on every existing object.
*Watch-out:* catalog `.tres` files store corners in NW/NE/SE/SW order while
`get_cell_corner_heights` returns NW/NE/SW/SE; the per-object verification
test must apply that corner reordering (indices 2/3 swapped), not assume the
raw arrays align.

### D3: Patch shares the octagon's silhouette, draped on the tile's two planes
The patch boundary is the same chamfered octagon as the flat cells
(`_octagon_local_xz`: `CELL_COVERAGE` 0.95, `CORNER_CHAMFER` 0.10), centered
on the cell — single source of truth for both paths, so corner cut size and
inset line up edge for edge. The octagon is split along the `pick_diagonal`
crease at the two points where that diagonal crosses it (the midpoints of the
two chamfer edges it joins); each half's vertices are evaluated on the terrain
triangle that half sits in, at `PLANE_Y_OFFSET` above the plane.
*Why:* the terrain tile is a two-triangle tessellation of the four corner
heights, so evaluating the patch on the same two planes reproduces the
rendered surface exactly — the outer silhouette stays the octagon, and no
patch triangle straddles the crease.
*Rejected (smoke test):* sampling each octagon vertex's Y from
`get_height_at_world_smooth` (bilinear) while keeping a fan fold along an
inset chord. Bilinear differs from the tile's planar halves by up to
`|h_nw+h_se-h_ne-h_sw|/4` (~0.20 m for a one-step corner, ~0.41 m for a
saddle) — far more than `PLANE_Y_OFFSET` (0.025 m) — so the patch sank below
the terrain and the fold bled through. Folding along the inset chord (rather
than the true cell diagonal) also chorded across the ridge. Planar, ramp, and
2-step cells were exact either way, which is why only tent/saddle cells bled.

### D4: Per-cell `MeshInstance3D` with a small slot pool; three shared materials
Each non-flat rendered cell gets one `ArrayMesh` (12 vertex positions, 24 index
entries — two crease-split 6-gons) on a `MeshInstance3D` whose
`material_override` is one of three shared
unshaded transparent `StandardMaterial3D`s (the existing white/green/red
colors, `CULL_DISABLED`, `vertex_color_use_as_albedo` not needed — material
albedo carries the state). Slots are reused from a bounded pool: when the
rendered non-flat cell set changes (white window slides, cursor moves a
different cell in or out), freed slots are taken and their `ArrayMesh` rebuilt
in place. Rebuilds happen on set membership change, never per frame.
*Why:* the per-corner Y values rule out a shared-mesh `MultiMesh`; the window
makes at most a few dozen non-flat cells, so a handful of draw calls is
negligible and the churn is bounded by cell-step frequency (the original #352
concern was per-frame allocation, which this avoids). `ponytail:` note in
code marking the pool cap as the upgrade point if profiling ever disagrees.
The flat-cell octagon `MultiMesh` path stays exactly as today.

### D5: Flat gate on cell type, shape from corners
`_rebuild()` partitions each resolved cell: cell data with `type == "clear"`
or empty data → octagon path (unchanged behavior, including the HIDDEN rule);
`type == "slope"` → patch builder on the cell's corner heights. The builder
itself is type-agnostic (it works for any corner pattern, including future
cliff/ramp cell data), so the gate only chooses between the two visual styles.

### D6: "Matching" acceptance gate: per-object catalog/GLB comparison
For every slope-family object and all four directional variants
(`games/ts/terrain_objects/slope0*_*.tres`, `slope17*_*.tres`,
`slope_saddle2_*.tres`): build the patch from the object's baked corners
(after the NW/NE/SE/SW → NW/NE/SW/SE reordering) and assert (a) the four
vertex positions equal the corresponding GLB submesh corners within epsilon
(submesh resolved via the object's `art_data` entry: its `submesh_id`, or the
object's base id when empty, matched directly against the GLB node names —
all are snake_case), and (b) the internal diagonal matches `derive_crease`.
Planar families pass on vertex positions regardless of the baked internal
diagonal (it is invisible). Spike 1.1 confirmed the chain end-to-end on the
canonical `_n` frame and found one deviation: `slope_saddle2` (a
hand-authored bake) is split along the low diagonal {NE,SW} while the corner
data and `derive_crease` call for the high diagonal {NW,SE}. The patch
follows the corner data (the true surface); the deviation is pinned by the
per-object test as the documented exception, not chased.

## Risks / Trade-offs

- [A baked GLB uses a different internal diagonal than the rule] → spike
  1.1 settled it: only the hand-authored `slope_saddle2` node deviates (low
  diagonal vs the rule's high diagonal). The patch follows the rule; the
  per-object test carries the deviation as an explicit expected value for
  that one node.
- [`slope_saddle2` hand-baked geometry deviates from its corner data] → the
  highlight follows the data (spec'd as authoritative); deviation documented
  with the test that pins it.
- [Draw-call growth when a cursor window covers many non-flat cells] →
  bounded by the existing window-radius constant (a few dozen instances at
  most; each a trivial 2-triangle mesh). `ponytail:` comment names
  batching as the upgrade path only if profiling flags it.
- [Pool churn on fast mouse movement (window slides cell by cell)] → slots
  are reused, not allocated; worst case is rebuilding a handful of 12-vertex
  meshes per cell step, orders of magnitude below the pre-#352 per-frame
  allocation rate.
- [Through-the-fold bleed on tent/saddle cells] → resolved by D3: the patch is
  draped on the tile's two planes (crease-split octagon), so it matches the
  rendered surface. `slope_saddle2` remains the documented exception (its
  hand-authored GLB bakes the opposite diagonal) and may still show a small
  artifact on those cells.
- [Corner-order slip (catalog NW/NE/SE/SW vs world NW/NE/SW/SE)] → the
  per-object test applies the reordering to catalog data before comparison,
  so a swapped order fails the test instead of silently rotating creases.

## Migration Plan

Single branch (`feat/386-terrain-matched-highlights`); no data, scene, or
resource format changes. Spec delta on `placement-grid-overlay` is applied at
archive time per the repo's OpenSpec workflow. Rollback is reverting the
branch; the overlay falls back to today's flat-octagon behavior for all cells.

## Open Questions

Resolved by the 1.1 spike (2026-09-06, throwaway script over the 24 slope
objects, the GLB submeshes, and `derive_crease`):

- The engine split rule matches the baked `crease` field of **all 24** slope
  object variants (24/24). No per-family override table is needed.
- Rotation covariance checked for all 18 non-canonical variants: stored
  variant corners equal `rotate_corners(canonical, t)` exactly, and the
  world-frame diagonal rule is covariant under the tool's permutation — the
  catalog→world reorder (indices 2/3 swapped) is the only order conversion
  the implementation needs.
- GLB cross-check (canonical `_n` frame): `slope_edge` (planar),
  `slope_corner`, `slope_tri`, `slope_steep`, and `slope_saddle` all use
  exactly the rule's diagonal; the only deviation is the hand-authored
  `slope_saddle2` node (splits along the low diagonal). Documented exception,
  the patch follows the corner data.
- Decided: data-exact (rule) wins over art-exact (baked diagonal) — the
  canonical `derive_crease` rule is the project's ground truth; placeholder
  art is a visual approximation and saddle2 is its only deviating node.
- Confirmed mechanics: runtime corner heights come from
  `get_cell_corner_heights` (world order NW/NE/SW/SE); the mesh local corner
  (0,0) sits on the cell's NW corner with x→east, z→south (the `_n` frame's
  catalog order); baked heights are n × `HEIGHT_STEP` (0.815) within
  0.005; submesh resolution is object `art_data` → `submesh_id`/base id →
  GLB node name (string-equal).
